# Dynamic filtering for Data Grid 2 and Gallery: grilling notes

Vocabulary lives in the root `CONTEXT.md` (Fixed Filter, Dynamic Filter, Filter Set).

## Settled

- **Intent (Q1/Q2):** the end user builds a Filter Set of Dynamic Filters, combined with AND only. The developer sets defaults and exclusions.
- **Story (Q6):** a user adds several filters, such as a date and a text filter, joined by AND. Presentation is undecided and may not be a menu, so nothing in the model assumes a container.
- **Persistence (Q5/Q13):** the Filter Set survives a reload when persistence is enabled. It reuses the existing `storeFiltersInPersonalization` (Data Grid 2) and `storeFilters` (Gallery) settings. Saved filters that no longer map to a valid attribute and operator are dropped silently.
- **Rows (Q10):** each row has an attribute picker, an operator and a value. "Add" appends a row.
- **Vocabulary (Q7/Q23):** Dynamic Filter, Filter Set, Fixed Filter, Filter Field, Filtering Mode. Query-builder terms (Query, Rule) were rejected because Mendix already uses them for XPath/OQL queries and Rule documents.
- **Exclusivity (Q12):** a list-style widget uses either Fixed Filters or a Filter Set, never both.
- **Filterable attributes (Q14):** the developer lists filterable attributes explicitly, each with its own label. They are not derived from columns, and column visibility (`visible`, `hidable`) has no effect on which attributes can be filtered.
- **Filtering mode (Q21):** a "Filtering mode" property with the values `Fixed filters` | `Dynamic filters`, default `Fixed filters`. Dynamic mode hides the column `filter` slots and `columnsFilterable`. `filtersPlaceholder` is never hidden, because it renders the grid header, which can hold more than filters (buttons, for example). Fixed configuration is kept when the mode switches.
- **Filter kind (Q16):** the filter kind (text, number, date, enumeration) is inferred from the attribute type. For each entry the developer specifies only the attribute, the label and, for enumerations, a set of values. Associations are not supported in v1. The kind is inferred exactly as for column filters, by reusing `attrgroupFilterStore` (`widget-plugin-filtering/src/stores/input/store-utils.ts`) unchanged (Q26).
- **Persistence keys (Q15):** the whole Filter Set is saved as one entry under a fixed key in the existing personalization blob, and stays out of `settingsHash`, so editing Filter Fields never resets column widths, order or sort. Each saved row refers to its Filter Field by a **developer-specified key**: a required plain string, checked for uniqueness in `consistency-check.ts`. The label is a separate, translatable `textTemplate`. Neither labels (they get translated and renamed) nor attribute ids (one field per attribute is too restrictive) are used as keys. Rows whose key no longer exists are dropped silently.
- **Enumeration values (Q27/Q28):** this mirrors the dropdown filter. By default the field offers every enumeration or Boolean value, in enumeration order, with the Mendix captions. Optionally, a top-level "Enumeration options" list of `fieldKey`, `caption` (textTemplate) and `value` entries **replaces** the automatic values for that Filter Field. A consistency check verifies that each `fieldKey` points to an existing enumeration Filter Field.
- **Operators (Q11):** each kind reuses the operator set of the matching existing filter widget unchanged (text, number, date, including "between"). Enumeration Dynamic Filters are always multi-select ("is one of"), with the selected values joined by OR inside the row. Rows are still joined by AND.
- **Timing (Q17):** settled by precedent. Rows apply live, the same way the existing widgets do (text and number after the debounce, dates immediately). An incomplete row adds no condition.
- **Rows (Q18):** two rows can use the same Filter Field, for every kind. Each row has a remove control, and there is a "Clear all".
- **Delivery (Q9/Q19):** built into Data Grid 2, not a separate widget. An explicit mode property on the grid flips between the two behaviors, so the grid enforces the exclusivity. This replaces the earlier "standalone widget, developer lists attributes" decision.
- **Scope (Q20):** v1 ships in both Data Grid 2 and Gallery. The Filter Field model, row builder and persistence live in a shared package. Gallery gets the same `filteringMode`, `filterFields` and `filterFieldOptions` properties and persists through `storeFilters`. Gallery has no column filters, so Dynamic mode hides nothing there except what the header shows at runtime (see Q25).
- **Defaults (Q22):** no developer defaults in v1. The Filter Set starts empty on first load. Defaults can be added later without changing the model.
- **Header filter widgets in Dynamic mode (Q25):** not supported. Data Grid 2 and Gallery provide a separate context that tells children the widget is in Dynamic mode. Any filter widget placed in the header renders an error alert saying the widget doesn't support filter widgets in Dynamic mode. Other header content (buttons, Drop-down sort) renders as usual. This is runtime only, because consistency checks can't see the widget types inside a slot.
- **Debounce (Q29):** hard-coded to 500 ms for text and number rows, with no property in v1. A widget-level property can be added later if someone needs it.
- **Schema version (Q30):** no bump. `dynamicFilters` is an optional field in the existing blob (Data Grid 2 `schemaVersion: 3`, Gallery `version: 1`), and a missing field means an empty Filter Set. A bump would drop every user's saved layout, because both widgets reject the whole blob on a version mismatch (`GridPersonalizationStore.ts:143`, `GallerySettingsSync.service.ts:64`).

## Open

- **Column menu (parked):** if column filters later move into a column menu, that must be reconciled with Dynamic mode. Everything else is settled.

## Presentation

- **Container (Q32):** the builder lives in the widget header (`WidgetHeader.tsx` / `GalleryHeader.tsx`, the area that renders `filtersPlaceholder`). It's inline, not behind a trigger: every row (field, operator, value, remove) is always visible, along with "Add filter" and "Clear all". The header grows by one line per row.
- **Placement (Q33):** the builder renders below the `filtersPlaceholder` content, inside the same header element (`widget-datagrid-header` / `widget-gallery-header`). In Dynamic mode the header always renders, even when the slot is empty (today both headers return `null` when it's empty).
- **Empty state (Q34):** with no rows, the builder shows only "Add filter". "Clear all" is hidden until there's at least one row. "Add filter" appends a blank row and moves focus to that row's field picker.
- **Value inputs (Q35):** rows reuse the existing filter UI: `InputWithFilters` for text and number, `EnumFilterContainer` for enumeration and Boolean, and `DatePicker` for dates. `DatePicker` (and `CalendarIcon`) move out of `datagrid-date-filter-web` into a shared package. For text and number, the operator control is the `FilterSelector` built into `InputWithFilters`.
- **Field picker (Q36):** the `Select` control from `widget-plugin-dropdown-filter/src/controls/select`, so it matches the enumeration value picker. Enumeration rows have no operator control (they're always "is one of"), and CSS keeps the columns aligned.
- **Changing a row's field (Q37):** if the new field has the same kind (text, number or date), the operator and value carry over and the row keeps filtering. If the kind changes, the row resets to that kind's default operator and an empty value. Enumeration to enumeration always resets, because the allowed values differ.
- **Narrow widths (Q38):** the widget doesn't control the layout. The row list uses `flex-wrap`, so rows flow as a list. A row's own controls don't wrap: if a row is wider than the header, the excess is clipped with `overflow: hidden`. There are no breakpoints or container queries.
- **Remove control first (Q38a):** the ✕ is the first control in a row (`✕ [Field] [operator] [value]`), so clipping only ever cuts off the end of the value and every row can still be removed.
- **Focus and screen readers (Q39):** every interactive element keeps its default tab index, so Tab follows normal browser order, and there's no roving tabindex. The focus moves below happen whether the action was triggered by keyboard or mouse. After "Add filter", focus goes to the new row's field picker. After removing a row, it goes to the ✕ of the row that took its place, or the new last row's ✕, or "Add filter" if no rows are left. After "Clear all", it goes to "Add filter". The rows are a `<ul>`/`<li>` list. Each ✕ is a `<button>` labelled `removeFilterAriaLabel` + field label (for example "Remove filter Status"). The field picker is labelled by a new `filterFieldAriaLabel` text (default "Filter field"). Reused controls keep their existing labels. There's no live region.
- **Studio Pro preview (Q40):** unchanged. The design-mode preview shows only the existing `filtersPlaceholder` drop zone, and the builder appears only at runtime.
- **Row limit (Q41):** no limit on the number of rows.
- **Styling (Q42):** a new partial `_dynamic-filters.scss` in `modules/data-widgets/src/themesource/datawidgets/web/`, imported from `main.scss` and using `variables.scss`. Class names follow the repo's Bootstrap-style dash convention, not pure BEM, and the block is shared by both widgets: `widget-dynamic-filters`, `dynamic-filters-list` (`<ul>`), `dynamic-filters-row` (`<li>`, `overflow: hidden`), `dynamic-filters-remove`, `dynamic-filters-field`, `dynamic-filters-operator`, `dynamic-filters-value`, `dynamic-filters-actions`, `dynamic-filters-add`, `dynamic-filters-clear`. Buttons use Atlas classes (`btn btn-secondary` for Add, `btn btn-link` for Clear all). Reused controls keep their existing classes and styles, so the partial only handles layout (flex-wrap, gaps, alignment).
